# Закупки: потребности → закупки → договоры (MVP)

MVP по ТЗ «Потребности, закупки и договоры (редакция 2)». Python 3.9+, Django 4.2, SQLite (PostgreSQL — через переменные окружения).

Главная идея из ТЗ реализована так: **статус живёт у позиции, а не у СЗ**. Закупщик собирает позиции из разных СЗ в закупку, одна позиция может делиться между поставщиками, один договор может включать позиции нескольких СЗ, а статус СЗ считается из статусов её позиций.

## Запуск (локально / демо)

```bash
./start.sh
```

Скрипт создаст виртуальное окружение, установит зависимости, создаст базу с демо-данными и запустит сервер на http://127.0.0.1:8000.

Вручную:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_demo          # --reset — пересоздать демо-данные
.venv/bin/python manage.py runserver
```

Тесты: `.venv/bin/python manage.py test core`

## Сценарий показа (≈10 минут)

1. **head** → «Входящие» → СЗ «Калькуляторы» → утвердить. Показать, что можно отклонить отдельную позицию с причиной (СЗ №4 так уже утверждена частично).
2. **buyer** → «Пул потребностей»: позиции из разных СЗ, фильтры, группировка по категории, подсветка дублей, срочные, «остаток от закупки №2» (частичное покрытие, п. 6.2).
3. «Выбрать дубли» → «Создать закупку из выбранных» → вкладка «Поставщики и запросы»: добавить поставщиков (фильтр по категориям), печатная форма запроса со **сводными строками** (п. 6.1), ссылка для поставщика.
4. «Ввести КП» — таблица с быстрым вводом (Enter/стрелки), импорт из Excel по шаблону. Открыть ссылку поставщика в другом браузере — поставщик заполняет КП сам.
5. Закупка №2 → «Сравнение» (минимум по строке подсвечен, итоги, «лучшее по каждой строке», экспорт в Excel) → «Договоры»: три договора, у OfficeMag — **спецификация к рамочному договору**.
6. **director** → «Входящие» → закупка №3 → согласовать. Затем **buyer** оформляет договоры.
7. Договор → «Спецификация» (позиция, СЗ, инициатор, поставлено, оплачено) → «Обмен с 1С»: выгрузка XML/JSON/Excel, загрузка поступлений (шаблон скачивается там же).
8. **ivanov** → «Реестр СЗ» → СЗ №2: по каждой позиции видно закупку, договор, поставщика, покрытие и поставку; уведомление «По вашей СЗ №2 поставлено: …».
9. **buyer** → «Отчёты»: покрытие потребностей, срок цикла, экономия (в т.ч. против прошлогодней цены), активность поставщиков.

## Что реализовано по пунктам ТЗ

| Пункт | Где |
|---|---|
| 3. Модель и правила целостности | `core/models.py`, `core/services.py`. Позиция одновременно только в одной активной закупке (ограничение в БД). Строка договора → ровно одна позиция. Превышение количества — только с подтверждением. Договор — один поставщик, позиции любых СЗ. Изменение позиций после отправки СЗ запрещено |
| 4.1 Статусы позиции | Вычисляются из фактов (`services.compute_status`): согласование, закупка, решение, договоры, поступления, отзыв, закрытие. «В договоре (остаток закрыт)» — через отзыв остатка |
| 4.2 Статус СЗ | Сводка «10 позиций: 3 в пуле…» + укрупнённый статус Новая / В работе / Исполнена / Проблемная |
| 4.3 Статусы закупки | Черновик → Запрос КП → Сбор КП → Анализ → Решение принято → Договоры оформлены → Закрыта; «Отменена» возвращает позиции в пул |
| 4.4 Договор | Черновик → На подписании → Подписан → Исполняется → Исполнен → Закрыт; оплаты и поступления разносятся построчно |
| 5. Шаги 1–9 | Все экраны; согласование решения по порогам суммы (настраиваются в админке: «Правила согласования решений») |
| 6.1 Консолидация | В лоте — отдельные строки, в запросе КП — сводная; цена сводной применяется ко всем; при выгрузке в 1С можно свернуть (флажок) |
| 6.2 Частичное покрытие | Остаток автоматически возвращается в пул с пометкой «остаток от закупки №N» |
| 6.3 Дробление | Решение — матрица «позиция × поставщик», количества можно делить |
| 6.4 Отзыв | Из пула — сразу; из закупки — запрос закупщику (запросы КП помечаются «к корректировке»); из договора — запрещено |
| 6.5 Изменение количества | Запрещено; «Копировать» СЗ — для добавки |
| 6.6 Срочные | Флаг, фильтр, подсветка, SLA-напоминание через N дней без движения |
| 7. Экраны | Реестр СЗ, карточка СЗ, пул, карточка закупки (7 вкладок), ввод КП, сравнение, карточка договора, дэшборд закупщика |
| 8. 1С | См. ниже |
| 9. Отчёты | 4 отчёта + выгрузка в Excel |
| 10. Права | Раздел в ТЗ пустой — предложена матрица ролей (страница «Роли и права»), её нужно согласовать с клиентом |

## Интеграция с 1С

В MVP — **обмен файлами**, это самое простое для 1С-программиста и не требует доступа к базе 1С:

* **Выгрузка договоров** (XML / JSON / Excel): договор, контрагент (БИН), спецификация построчно; в каждой строке поле `IDПозиции` вида `СЗ-12/3`. Опция «сворачивать одинаковые позиции» — для бухгалтерии (ID идут через `;`).
* **Загрузка поступлений** (Excel / CSV / JSON / XML), колонки: `Договор, Дата, НомерДокумента, IDПозиции, Номенклатура, КодНоменклатуры, Количество`. Сопоставление: по `IDПозиции` — автоматически; иначе по коду/названию номенклатуры в договоре — с ручным подтверждением закупщика.
* **Загрузка оплат**: `Договор, Дата, НомерДокумента, Сумма`. Оплата по договору целиком распределяется на позиции пропорционально сумме строк — **справочно, не для бухучёта** (это нужно явно зафиксировать в договоре с клиентом, п. 8 ТЗ).

На следующем этапе тот же формат можно отдавать/принимать через HTTP-сервис 1С (REST) или по расписанию из папки обмена — логика сопоставления уже написана (`core/onec.py`).

## Команды управления

| Команда | Назначение |
|---|---|
| `import_refs файл.xlsx [--dry-run]` / `--template` | загрузка справочников заказчика / получить шаблон |
| `scheduler` | фоновый процесс: `run_periodic` раз в час, `onec_exchange` каждые 10 мин (на сервере — отдельный контейнер) |
| `run_periodic` | автозакрытие поставленных позиций, SLA-напоминания, пересчёт статуса «Проблемная» |
| `onec_exchange [--dir путь]` | обмен с 1С через папку (in/out/archive/error) |
| `recalc_all` | полный пересчёт количеств и статусов (после ручных правок в БД) |
| `seed_demo [--reset]` | демо-данные (только при `DEMO_MODE=1`) |

Параметры (дни, пороги, папки) задаются переменными окружения — см. `.env.example`.

## Вопросы к клиенту перед следующим этапом

1. Права (раздел 10) — согласовать предложенную матрицу.
2. Пороги согласования решения и кто согласует (сейчас: ≥ 1 млн — директор, ≥ 5 млн — финдиректор).
3. Портал поставщика — оставляем ссылку без регистрации или нужен личный кабинет?
4. 1С: какая конфигурация (БП / УТ / ERP), файловый обмен или HTTP-сервис, нужно ли сворачивать консолидированные строки.
5. Уведомления: только в системе или ещё e-mail / Telegram.
6. Через сколько дней автозакрывать поставленные позиции и какой SLA для срочных.
